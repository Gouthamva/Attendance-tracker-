Deploy Goutham on GitHub Pages

This page works inside Canva with its Canva Sheet. For a standalone GitHub Pages copy, configure Supabase first: GitHub Pages hosts only the frontend, while Supabase stores the class register.

  1. Create the backend: Create a Supabase project. In its SQL Editor, create the public.class_attendance table using the SQL below. Configure and test Row Level Security policies for SELECT and INSERT and roster-only DELETE before publishing. The example SQL does not grant access by itself.
  2. Find the public connection values: In Supabase project settings, copy the Project URL and publishable/anon key. In the index.html script below, replace the empty strings in GITHUB_SUPABASE_URL and GITHUB_SUPABASE_ANON_KEY. Never put a service-role or secret key in frontend code. You can also use the connection fields below for this page session, but they do not configure a published copy.
  3. Publish the frontend: Add this index.html to the root of a GitHub repository and push to your main branch. In the repository's Settings → Pages, choose Deploy from a branch, select main and /(root), then save. Open the Pages URL after deployment completes.
  4. Check the base path: A project Pages site is served at https://username.github.io/repository-name/. This single HTML page uses relative page URLs, so no router base path is needed. If you later add a build tool or assets, set its base/public path to /repository-name/ (or / for a user site) and use relative asset paths. Canva-only /_sdk/ scripts are unavailable on GitHub Pages; the standalone copy uses Supabase instead.
  5. Verify: Open the published page, add a test student and subject, mark today's attendance, then refresh and check Reports and the Supabase table. Previous marks remain read-only. Do not publish real student details with unrestricted anonymous policies; use a private deployment with appropriate access controls for private class data.

Supabase table setup

Create this table in the Supabase SQL Editor before connecting. Supabase must have appropriate Row Level Security policies for your intended users. An anon key is public by design: it is not a secret or a substitute for access control. Never enter a service-role key here.

create table public.class_attendance (
  id bigint generated always as identity primary key,
  source_id text not null unique,
  kind text not null,
  name text not null default '',
  reference_id text not null default '',
  attendance_date date,
  status text not null default '',
  created_at timestamptz not null default now()
);
alter table public.class_attendance enable row level security;
create unique index one_mark_per_student_session
  on public.class_attendance (name, reference_id, attendance_date)
  where kind = 'attendance';
-- Prevent changes or deletion of any attendance mark, including via API.
create function public.protect_attendance() returns trigger
language plpgsql as $$ begin
  if old.kind = 'attendance' then
    raise exception 'Attendance records are immutable';
  end if;
  return old;
end $$;
create trigger lock_attendance before update or delete
  on public.class_attendance for each row
  execute function public.protect_attendance();

For GitHub Pages, enable SELECT, INSERT, and roster-only DELETE through appropriately scoped RLS policies. Without a trusted authentication layer, a public anon key cannot securely restrict access to a private class; do not publish real student information under open anonymous policies. Existing Canva Sheet records are not automatically backfilled. Publish this index.html at your repository root and enable GitHub Pages from the main branch.
